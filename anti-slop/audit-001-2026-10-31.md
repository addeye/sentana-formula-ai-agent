## Prioritized findings for selection

### 1. HIGH: Input boundaries do not meet 3:1 non-text contrast

**Rule:** R-25 and antislop-human non-text contrast (WCAG 1.4.11).

**Evidence:** `tailwind/login.html:20,27` specifies white input backgrounds and `border-slate-300`; `tailwind/admin.html:49-52` uses `border-slate-400` for editor fields on the white editor surface declared at line 45. The shared stylesheet does not supply a stronger resting input border (`demo.css:9`). These inputs depend on their borders to identify their extent.

For reference sRGB slate colors, `#cbd5e1` on white is **1.48:1**, and `#94a3b8` on white is **2.56:1**, below 3:1. Tailwind v4 emits OKLCH palette values, so these figures are reference-token calculations, not browser measurements; actual rendered colors still need measurement. The hardcoded `#94a3b8` border on white `.demo-edit` (`demo.css:28`) is exactly 2.56:1, although its readable button label means the border alone does not establish a WCAG failure for that button.

**Suggested scope:** strengthen necessary input boundaries; verify actual compiled Tailwind colors and Bootstrap input boundaries in-browser. Do not darken every decorative divider indiscriminately.

### 2. HIGH: Bootstrap login links do not receive the intended 44px hit area

**Rule:** R-03, project minimum touch target.

**Evidence:** `bootstrap5/login.html:31-32` places two ordinary inline `.demo-link` anchors inside the card without block/flex sizing. `demo.css:6` gives `.demo-link` a `min-height: 44px`, but minimum height does not apply to non-replaced inline elements. No rule changes these anchors to block or inline-flex. Their painted/tappable inline line boxes therefore do not gain the promised 44px height.

**Suggested scope:** make these links block/flex targets of at least 44px. Confirm wrapping and spacing at narrow widths. Do not confuse this project-specific 44px gate with WCAG 2.2 AA's separate 24px target-size criterion.

### 3. HIGH: Error recovery hides the keyboard-focused button without moving focus

**Rule:** R-32 and C-4, predictable keyboard operation across state changes.

**Evidence:** `demo.js:105` handles Retry by selecting normal mode and invoking `render()`, without a focus destination. `render()` hides `#error-state` at line 48. The Retry button is inside that container in both `bootstrap5/admin.html:43` and `tailwind/admin.html:43`. Keyboard activation thus leaves focus on a newly hidden control; the browser may reset focus to the document rather than a useful recovery destination.

Related continuity issue: `demo.js:91-95` always returns editor focus to Create, even after Edit was invoked from a table row (`demo.js:72`). This is not a focus trap, but it loses the user's row context.

**Suggested scope:** focus a visible recovery destination after Retry; restore the invoking row action after edit/cancel where it still exists. Note that `render()` replaces row elements, so storing the old DOM node alone is insufficient after saving.

### 4. HIGH: Desktop disclosure depends on JavaScript to make navigation reachable

**Rule:** R-32 / C-4, accessible navigation under script failure; reduced-resilience finding, not a claim that the full JavaScript demo must work without scripts.

**Evidence:** Both `bootstrap5/admin.html:14` and `tailwind/admin.html:14` initialize `<details id="navigation">` closed. `demo.css:33-36` hides its summary at desktop widths. Only `demo.js:136-139` opens it on desktop. If this script fails or is blocked, desktop links remain inside a closed disclosure with no visible or keyboard-operable summary to reveal them.

**Suggested scope:** retain an operable desktop disclosure until script initialization succeeds, or initialize markup open and collapse it on mobile through the existing script. This issue does not follow merely from unavailable framework styles: `demo.js` is local and Bootstrap CSS failure alone does not prevent it from executing.

### 5. LOW: Canonical preview deliberately diverges from the prescribed mobile shell

**Rule:** R-05 / C-1, fidelity to stated architecture, not an aesthetic preference.

**Evidence:** `references/web.md:14` prescribes a mobile drawer/offcanvas with dark backdrop, and lines 16-18 prescribe a fixed-height topbar with mobile menu action. Both templates instead place an in-flow `<details>` before the workspace (`bootstrap5/admin.html:14-24`, `tailwind/admin.html:14-24`). `demo.css:18` uses a minimum rather than fixed topbar height. `templates/README.md:50` and `references/web.md:97` honestly document the disclosure exception, so this is **not** a hidden or dead-control defect. However, `SKILL.md:28` directs interactive implementations to begin from these templates, making the exception likely to propagate instead of the prescribed pattern.

**Suggested scope:** choose whether the minimal disclosure is the approved baseline or whether previews must demonstrate the drawer standard. Do not add tenant/profile/logout controls merely to make an unauthenticated inventory demo look enterprise-ready.

## Not findings

- `tailwind/login.html:25` contains `min-h-0`, but that alone does **not** prove a small target: the unlayered `button { min-height: 44px; }` in `demo.css:6` outranks normal layered Tailwind utilities. Browser measurement is required before reporting a failure.
- A toggle before the password input is not inherently an invalid focus order; the DOM follows its visible placement.
- Missing dark mode, offline bundles, profile menus, deletion, and pagination are not independently established defects in these explicitly bounded previews.
- Neutral text in a `role="alert"` is not an accessibility failure merely because it lacks a red border or icon.
- Sticky-column collision, mobile overflow, focus-ring visibility under framework overrides, and visual identity remain unverified, not passes or proven failures.
